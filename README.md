# 群邀请自动处理

收到群邀请时打印该群全部信息，按关键词与人数自动审批；入群后复核，不合格自动退群。

[![AstrBot 插件市场](https://img.shields.io/badge/AstrBot-%E6%8F%92%E4%BB%B6%E5%B8%82%E5%9C%BA%E5%85%A5%E5%8F%A3-ff69b4?style=for-the-badge)](https://cloud.astrbot.app/plugin/XingYunStar/astrbot_plugin_group_invite_auto_approve)

</div>

## 📖 简介

本插件面向 **aiocqhttp（OneBot v11）** 平台，处理机器人收到的**群邀请**：

- 收到邀请后采集该群全部可用信息，整块打印到 AstrBot 日志；
- 按**关键词**（群名称 / 群介绍 / 群公告）与**群人数**决定同意还是拒绝，两个条件为 **AND** 关系；
- 同意进群后可选地私聊邀请人、在群内发送欢迎消息与图片；
- **入群后复核**：先放机器人进群拿到真实资料，再判一次，不合格自动退群。

适合让机器人只放行主题相符的群（例如米游相关群），把无关邀请挡在外面，全程无需人工。

## ✨ 功能特性

- 🔍 **邀请即留痕**：每收到一个群邀请，就把该群的群号、名称、备注、人数、建群时间、等级、全员禁言、群主、管理员、群介绍、群公告整块写进日志；每个字段独立获取，任一接口失败都不影响其它字段，失败原因单独列出。
- ✅ **两种审批模式**：无条件同意全部邀请，或按条件判断（关键词 AND 人数），每项条件可独立开关。
- 🧭 **三态条件判断**：严格区分「明确不满足」与「拿不到数据」——协议端没给数据时不会误判成不满足，详见[判断规则](#rules)。
- 🚪 **入群后复核**：这是「机器人不在群里就拿不到群名 / 人数」的根本解法——先进群，用真实资料重新判断，不合格自动退出。
- 👋 **入群欢迎**：机器人最终留在群里就发送欢迎消息，可附带本地图片或图片 URL；同一群 10 分钟内只发一次。
- 💬 **通知邀请人**：同意 / 未满足条件各有一套可自定义文案，支持占位符，按**实际执行结果**发送，不会谎报成功。
- 🖥️ **WebUI 管理页**：可视化编辑全部配置，查看邀请记录与命中明细，还带「群号体检」「规则试算」两个离线调试工具。
- 🛡️ **抗事件截断**：入群通知被其它插件 `stop_event()` 截断时，仍能通过轮询兜底完成复核。

## 📦 安装

1. 在 AstrBot WebUI 的**插件市场**搜索 `astrbot_plugin_group_invite_auto_approve`，点击安装；
2. 安装完成后**重载插件**（或在插件管理页启用）；
3. 进入 **插件配置** 按需调整策略——默认配置即可直接使用。

| 项 | 要求 |
| --- | --- |
| AstrBot | `>= 4.24.2`（需要插件 Pages 功能） |
| 平台 | `aiocqhttp`（OneBot v11）；其它平台不会生效 |
| 依赖 | 无第三方依赖，`requirements.txt` 为空 |
| 开发与实测环境 | AstrBot **4.25.5** + [SnowLuma](https://github.com/SnowLuma/SnowLuma) **1.14.21** |

> [!NOTE]
> **关于 SnowLuma**：它是基于 NTQQ 进程注入的 OneBot v11 协议端实现，本插件在它上面开发与测试。
> 它从 **v1.14.21** 起才会返回真正的群简介字段，更早的版本上「群介绍」可能取到群公告的截断预览——
> 详见[已知限制](#limits)。
>
> 群简介的字段名在 SnowLuma 与 NapCat 上并不相同，插件**已自动兼容两者**：
> SnowLuma 用 `group_description`（≥ 1.14.21）或 `group_memo`（≤ 1.14.20），
> NapCat 用 `fingerMemo`（必要时自动补问 `get_group_detail_info`）。

> [!TIP]
> 也可以手动把插件目录放入 `AstrBot/data/plugins/astrbot_plugin_group_invite_auto_approve/`，再重载插件。

## ⚙️ 配置

在 AstrBot WebUI 的 **插件管理 → 群邀请自动处理 → 插件配置**中修改，也可以直接用插件自带的[管理页](#pages)——两边读写同一份配置。

### 审批策略

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| **自动同意所有群邀请** | 关 | 开启后无条件同意全部群邀请，**优先级高于下方所有条件判断** |
| **满足以下要求时自动同意 · 关键词** | 开 | 群名称 / 群介绍 / 群公告**任意一处**包含**任一**关键词即满足 |
| └ 关键词列表 | `原神`、`星穹铁道`、`绝区零` | 参与匹配的关键词 |
| **满足以下要求时自动同意 · 人数** | 开 | 需**同时**满足「大于下限」且「少于上限」 |
| └ 群人数下限 | `0` | 群人数需**大于**该值 |
| └ 群人数上限 | `3000` | 群人数需**少于**该值 |
| **群名 / 人数拿不到时怎么办** | 进群试用 | `approve` 进群试用 / `skip` 不进群也不回复，详见[判断规则](#rules) |
| **未满足条件时自动拒绝群邀请** | 关 | 关：保持待处理，不做任何操作；开：主动调用接口拒绝 |

> [!NOTE]
> 两个条件开关**全部关闭**时，插件不处理群邀请——既不自动同意，也不自动拒绝，也不发送任何消息。

### 入群后复核

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| **入群后重新校验，不满足条件则自动退群** | 开 | 进群后用真实资料重新判断关键词与人数，不满足自动退出 |
| └ 入群后等待多少秒再校验 | `3` | 给协议端同步群资料的时间 |
| └ 可被 QQ 强行拉人的群人数上限 | `50` | 见[QQ 会强行把机器人拉进小群](#force-join)；填 `0` 关闭该行为 |
| └ 豁免名单 | 空 | 名单内的 QQ 号拉群时不触发自动退群；AstrBot 配置里的**数字**管理员账号自动豁免 |

> [!IMPORTANT]
> 开启本项后，「群名 / 人数拿不到时怎么办」会被**强制按「进群试用」生效**，否则复核永远不会触发（机器人不进群就没有入群通知）。插件会在启动日志、管理页和决策记录三处明确说明这一点，不会静默改写配置。

### 消息通知

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 同意进群后对邀请人发送消息 | 开 | 私聊邀请人 |
| └ 消息内容 | `已同意进群~` | 支持占位符 |
| 未满足条件时对邀请人发送消息 | 开 | 私聊邀请人 |
| └ 消息内容 | `不满足以下条件：\n{reasons}` | 未写 `{reasons}` 时会自动追加到消息末尾 |
| └ 自定义额外消息 | 空 | 追加在「未满足条件」消息之后，留空不发送 |
| 当同意进群后发送消息 | 开 | 在群内发送欢迎消息 |
| └ 消息内容 | `我是机器人，欢迎使用` | 支持占位符 |
| 当同意进群后同时发送图片 | 空 | 本地文件绝对路径或 `http(s)` 图片 URL，留空不发送 |

**可用占位符**

| 占位符 | 含义 |
| --- | --- |
| `{group_name}` | 群名称 |
| `{group_id}` | 群号 |
| `{group_remark}` | 群备注 |
| `{group_memo}` | 群介绍（优先协议端返回的真群简介，取不到时退回 `group_memo` 原值） |
| `{member_count}` / `{max_member_count}` | 当前人数 / 人数上限 |
| `{create_time}` | 建群时间 |
| `{inviter}` / `{inviter_id}` | 邀请人昵称 / QQ 号 |
| `{keywords}` | 当前配置的关键词列表 |
| `{reasons}` | 自动生成的「未满足条件」清单 |

> [!NOTE]
> `{reasons}` 未写进模板时会自动追加到消息末尾；未知占位符原样保留，不会报错。

### 高级

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| 收到群邀请时在日志打印此群所有信息 | 开 | |
| 尝试获取群公告参与关键词匹配 | 开 | 群公告需要机器人已在群内，未入群时通常读不到 |
| 管理页保留的邀请记录条数 | `100` | |

<a id="rules"></a>

## 🧭 判断规则

### 优先顺序

1. **自动同意所有群邀请**开启 → 无条件同意，不再判断任何条件；
2. 否则判断已开启的条件，多个条件同时开启时为 **AND**（全部满足才同意）；
3. 条件全部关闭 → **不做任何处理**。

### 条件的三种状态

判断时严格区分「明确不满足」与「拿不到数据」：

| 状态 | 出现场景 | 处理方式 |
| --- | --- | --- |
| ✅ 满足 | 读到数据且符合 | 继续判断其它条件 |
| ❌ 不满足 | **读到数据**但不符合 | 视为未满足 → 默认保持待处理 |
| ❓ 无法判定 | **协议端没给所需数据**（机器人不在群里时，群名 / 群介绍 / 群人数都可能拿不到） | **不当作不满足**，改走「群名 / 人数拿不到时怎么办」策略 |

> [!WARNING]
> **群人数不可能是 0。** 协议端对「机器人不在群内」的群恒返回 `0`，这只说明读不到。若把它当成「人数不满足」，任何没进过的群都会被挡在门外。

### 「进群试用」与「自动同意所有群邀请」的区别

这两个选项经常被混淆，但完全不同：

| | 进群试用（`approve`） | 自动同意所有群邀请 |
| --- | --- | --- |
| 适用对象 | 只有**群名 / 人数确实拿不到**的那部分邀请 | **全部**群邀请 |
| 是否判定条件 | ✅ 进群后按真实资料逐条判断 | ❌ 完全不判断 |
| 不符合条件时 | ✅ **自动退出该群** | ❌ **永不退出** |

所以「进群试用」是安全的：它只是把判断挪到进群之后做，而不是放弃判断。

### 入群后复核覆盖哪些入群

| 入群来源 | 是否复核 | 复核通过 | 复核不通过 |
| --- | --- | --- | --- |
| 本插件同意了邀请 | ✅ | 留在群里 + 发欢迎消息 | 通知邀请人后退群 |
| **不请自来**（QQ 自动拉小群、他人手动拉群） | ✅ | 留在群里 + 发欢迎消息 | 通知操作者后退群 |
| **重复邀请**（机器人已在群里且群人数小于阈值） | ✅ | 留在群里 + 发欢迎消息 | 通知邀请人后退群 |

> 欢迎消息的判定标准是「**机器人最终是否留在群里**」，而不是「谁点的同意」，因此三条路径都可能发送；同时加了 10 分钟的同群去重窗口，不会刷屏。

<a id="force-join"></a>

### QQ 会强行把机器人拉进小群

QQ 有一条硬性规则：**少于 50 人的群，不需要机器人同意就会被直接拉进去。** 这类入群机器人根本没机会审批，随之而来的请求事件看起来就像一次「重复邀请」。

如果不处理，人数下限这类条件就形同虚设。因此收到「重复邀请」时插件会先看群人数：

| 群人数 | 判断 | 行为 |
| --- | --- | --- |
| **小于** `force_join_max_members`（默认 50） | 属于「QQ 可强行拉人」的群 | 按配置条件**重新复核**，不合格则通知后**退群** |
| 不小于阈值 | 只可能是正常审批 / 管理员拉进去的 | 不质疑，直接回「已进群」 |

**安全边界**：自动同意所有群邀请开启时永不退群；条件全部关闭时不退群；豁免名单内的账号拉群不复核；人数未知时不做判断。

## ❓ 常见问题

<details>
<summary><b>收到邀请时群名 / 群人数是空的，是不是插件坏了？</b></summary>

不是。机器人**还没进群**时，QQ 只提供有限的公开信息，群名称 / 群介绍 / 群人数都可能读不到——这是 QQ 侧限制，不是插件故障。

插件为此做了三件事：日志里明确写出原因而不是只显示一个让人困惑的 `0`；额外调用申请收件箱接口补齐群名称与邀请人昵称；把这种情况判定为「无法判定」，按 `when_info_unavailable` 走「进群试用」，进群后用真实资料再判一次。

详见[已知限制](#limits)。
</details>

<details>
<summary><b>群介绍显示的是群公告内容？</b></summary>

在 **SnowLuma ≤ 1.14.20** 上确实如此：协议端把群简介与群公告合并成了一个字段，只要群里有公告，返回的「群介绍」就是公告的截断预览。

**SnowLuma v1.14.21 起已修复**，插件会自动使用新的 `group_description` 字段，无需任何配置。详见[群介绍字段与 SnowLuma 版本](#group-description)。
</details>

<details>
<summary><b>群公告一直读不到？</b></summary>

群公告走的是 QQ 群网页接口，需要机器人**已经在群内**。收到邀请时机器人还不在群里，因此关键词无法匹配公告，只能匹配群名与群介绍。

若关键词只写在公告里，建议同时把关键词加进群名或群介绍，或开启「入群后重新校验」让机器人进群后补判。
</details>

<details>
<summary><b>审批时报 <code>OIDB error 120161001 ... handle async message fail</code>？</b></summary>

这是协议端对审批请求的 flag 处理路径问题，插件已自动绕过。

协议端处理审批分两条路：`slreq:` 开头的 flag 会直接使用 flag 内的 `eventType`，而 QQ 服务器只接受「邀请卡片序列 + `eventType=2`」，走这条路注定失败；`invite:群号:邀请人QQ` 这种 legacy 形式才会去查卡片序列、使用服务器接受的参数。

插件的做法是：**只对 `slreq:` 开头的 flag**，在审批失败时自动改用 legacy 形式重试一次。canonical 形式仍会先试（万一协议端以后修好了这条路径也能用），两次都失败则如实报错，不会谎报成功、也不会给邀请人发「已同意进群~」。
</details>

<details>
<summary><b>机器人进群了，为什么没发欢迎消息？</b></summary>

欢迎消息只在「**机器人最终留在该群**」时发送，复核不通过（已退群）时自然不会发。若确认已留下但仍没收到，请检查「当同意进群后发送消息」开关是否开启，以及是否落在同一群 10 分钟的去重窗口内。
</details>

<details>
<summary><b>机器人已经在群里了，又收到一次邀请会怎样？</b></summary>

插件会先用群列表确认成员身份：已在群里就**跳过**审批接口调用（否则协议端会报 `handle async message fail`），同时仍然通知邀请人「已同意进群~」，因为对方想要的结果已经达成。若该群人数小于强行拉人阈值，还会按条件重新复核，不合格则退群。
</details>

<details>
<summary><b>关键词条件开启了但没配关键词？</b></summary>

该条件恒不满足。日志与私聊消息中都会提示「已开启关键词条件，但没有配置任何关键词」。
</details>

<details>
<summary><b>改了 <code>main.py</code> 需要重启吗？</b></summary>

需要重载插件；只改 `pages/` 下的静态资源刷新页面即可。
</details>

<a id="limits"></a>

## ⚠️ 已知限制

- **仅支持 aiocqhttp（OneBot v11）**：其它平台不会生效。
- **只处理群邀请**：`sub_type == "invite"` 的事件才处理，机器人主动申请加群（`sub_type == "add"`）与好友申请都会被忽略。
- **非成员群的资料限制**：机器人从未加入（或已退出）的群，协议端只能返回「空壳」——群名称 / 群介绍 / 群人数都拿不到。这是 QQ 侧限制，插件无法绕过，只能用「进群试用 + 入群后复核」应对。
- **群公告需要机器人已在群内**才能读取。
- **协议端字段差异**：群简介已自动兼容 SnowLuma 与 NapCat（见下节），但**建群时间与群等级目前只有 SnowLuma 返回**，NapCat 上这两项会显示为「未知」/ `0`。

<a id="group-description"></a>

### 群简介字段与协议端

群简介在不同协议端叫不同名字，插件会**自动选用正确的字段**，无需任何配置：

| 协议端 | 群简介字段 | 说明 |
| --- | --- | --- |
| **SnowLuma ≥ 1.14.21** | `group_description` | 真正的群简介 |
| **SnowLuma ≤ 1.14.20** | `group_memo` | 旧字段，协议端按 `announcement \|\| description` 拼出，**公告优先**；有公告时拿到的是公告的截断预览 |
| **NapCat** | `fingerMemo` | `get_group_info` 不返回任何群简介，插件会补问一次 `get_group_detail_info`（`richFingerMemo` 作兜底） |

也就是说，在 **SnowLuma ≤ 1.14.20** 上，关键词匹配「群介绍」时实际匹配到的可能是群公告。**升级到 1.14.21 及以上即可解决**；在旧版上插件仍能正常工作，只是在日志里标注「该项其实是群公告的截断预览」。

> [!NOTE]
> 机器人**尚未入群**时，QQ 的对应接口本身就不返回群简介，任何协议端版本都拿不到——这不是版本问题，插件会在成功入群后自动补全并重新判断。

各协议端返回的其余字段：

| 字段 | SnowLuma | NapCat | 影响 |
| --- | --- | --- | --- |
| `group_name` / `group_remark` | ✅ | ✅ | `{group_name}` / `{group_remark}` |
| `member_count` / `max_member_count` | ✅ | ✅ | `{member_count}` / 人数条件 |
| `group_all_shut` | ✅ | ✅ | 日志「全员禁言」 |
| `group_create_time` | ✅ | ❌ | `{create_time}`、日志「群创建时间」 |
| `group_level` | ✅ | ❌ | 日志「群等级」 |

### 入群通知可能被其它插件截断

AstrBot 的处理器循环在前一个插件调用 `event.stop_event()` 后会跳过后续处理器。若有其它插件把「机器人被拉进群」当作自己的通知处理并停止事件，本插件就收不到 `group_increase`，入群欢迎与复核都会静默失效。

插件为此内置两道**互相独立**的保障：

| 保障 | 做法 | 覆盖场景 |
| --- | --- | --- |
| ① 监听器高优先级 | `priority=100`，排在普通插件之前执行 | 正常收到通知，第一时间复核 |
| ② 入群轮询兜底 | 同意邀请后启动后台任务，每 2~5 秒查一次群列表，最多 90 秒 | 通知被截断、协议端不发通知等所有情况 |

两条路径互斥，只会有一条真正执行，不会重复发欢迎消息或重复复核。
